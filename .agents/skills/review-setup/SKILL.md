# Установка RDV AIR на Windows

Подготовь компьютер и проект так, чтобы следующий `review-init` получил задачу/MR и параметры конкретного ревью и запустил готовый CLI. Не оставляй установку Git, клонирование репозитория проверяемого проекта, настройку доступа, переменных окружения MCP или выбранного AI-агента на этап `review-init`.

Используй [setup-checklist.md](references/setup-checklist.md) как список результатов, а не как вторую инструкцию. Команды установки находятся в разделе [«Установка на Windows»](../../../docs/advanced-usage.md#установка-на-windows), Git и SSH — в [«Git-доступ и ветка задачи»](../../../docs/advanced-usage.md#git-доступ-и-ветка-задачи), MCP — в [«Подключить MCP»](../../../docs/advanced-usage.md#подключить-mcp). Пример конфигурации RouterAI находится в [opencode-routerai.example.jsonc](references/opencode-routerai.example.jsonc).

## Границы

- Этот skill поддерживает установку только на Windows.
- Не запускай `review-tasks init`, не создавай каталог задачи (task capsule) и не выполняй ревью. Это делает `review-init` после завершения настройки.
- До первого изменения выполняй только проверки из раздела 2. Перед установкой, клонированием, `git fetch`, созданием каталога, записью конфигурации или запуском сервиса сообщи пользователю, что будет сделано.
- Устанавливай отсутствующее ПО только после явной просьбы пользователя, например «установи». Если пользователь устанавливает компонент сам, дождись подтверждения и продолжи с его проверки.
- Не сканируй диски, соседние каталоги, посторонние Git-репозитории, идентификаторы SSH и пользовательские конфигурации. Работай только с путями, которые дал пользователь, текущей папкой `review-tasks` и стандартными путями выбранных компонентов.
- В репозитории проверяемого проекта разрешены клонирование, обновление удалённых ссылок через `git fetch` и настройка локального `core.sshCommand`, если для Git-доступа нужен описанный в инструкции обход кириллического SSH-пути. Не меняй remote, рабочее дерево, коммиты или ветки без отдельной просьбы пользователя.
- Не проси внешние токены, пароли и закрытые ключи в чате. Не читай и не выводи их значения. Для секретов внешних сервисов проверяй только `present` / `missing`; в конфигурации используй ссылки на переменные окружения. Локальный токен расширения — исключение: его можно сгенерировать, сохранить и показать пользователю для настройки расширения, в том числе в выводе BAT-мастера.
- Не запускай `opencode debug config`: итоговая конфигурация может раскрыть секретные значения. Не отправляй запрос к LLM для проверки авторизации, провайдера или модели: такой запрос может быть платным.
- Поддерживай только OpenCode V1 с major-версией `1`, установленный npm-пакетом `opencode-ai@1`. Не устанавливай `@opencode/cli`, OpenCode V2 или конфигурацию формата V2. Не используй `opencode upgrade` для обновления: обновляй только внутри major V1 командой `npm install -g opencode-ai@1`.

## 1. Определить исходные данные

Сначала используй текущую открытую папку как источник `review-tasks`. Определи, является она распакованным ZIP-архивом релиза или Git checkout публичной ветки `main`. Установка Python CLI не копирует skills: IDE видит их из открытой папки `review-tasks`.

Из запроса и текущей IDE определи всё уже известное. Остальные данные собирай по мере необходимости:

1. способ запуска ревью: вручную из IDE или из Jira;
2. выбранный AI-агент: Codex, Cursor или OpenCode;
3. необходимость RouterAI для OpenCode;
4. режим внешней проверки: MCP `off` или `required`;
5. локальный путь или Git URL репозитория проверяемого проекта;
6. каталог клонирования, если дан Git URL;
7. префикс задач проекта, например `RDV`;
8. каталог результатов `reviewsRoot`;
9. Git remote, обычно `origin`;
10. Git ref по умолчанию — предложи `<remote>/HEAD` для общей ветки проекта, если ссылка существует и указывает на нужную ветку; иначе уточни явный ref; ref конкретной задачи можно переопределить в `review-init`;
11. только для Jira — нужен ли поиск MR через GitLab API или достаточно TASK-режима.

Не задавай все вопросы заранее. Сначала проверь общесистемные компоненты, затем запроси данные репозитория проекта, после этого — только отсутствующие настройки выбранного способа запуска. Для каждого неизвестного значения объясни назначение и предложи конкретное значение по умолчанию.

Ключ задачи или MR нужны только при будущем запуске и при настройке не запрашиваются.

## 2. Начальная проверка без изменений

Проверь только:

1. Windows и наличие `winget`;
2. `git --version`;
3. `python --version` или `py --version`; нужна версия Python 3.11+;
4. исполняемый файл `review-tasks` и `review-tasks --help`;
5. готовую авторизованную IDE-сессию для ручного запуска; для Jira — наличие выбранного CLI: `codex --version`, `agent --version` или `opencode --version`; для OpenCode версия считается поддерживаемой только при major `1`;
6. если пользователь дал локальный репозиторий проекта — только существование пути, корень Git-репозитория и URL выбранного remote;
7. только для OpenCode — наличие `%USERPROFILE%\.config\opencode\opencode.jsonc` и `opencode.json`, не выводя содержимое целиком;
8. наличие обязательных переменных окружения выбранного режима как `present` / `missing`;
9. только для уже настроенного запуска из Jira — `/health` локального сервиса через loopback-адрес.

Если компонент работает, сохрани его. Не переустанавливай ради другого менеджера пакетов или пути. После ошибки расширяй диагностику только для отказавшего компонента.

## 3. Установить системные компоненты и RDV AIR

Git и Python 3.11+ обязательны. Если одного из них нет, сообщи об этом и предложи типовую установку через `winget`. Выполняй её только после ответа пользователя «установи» или равнозначного разрешения. Точные команды и проверки бери из [«Установка на Windows»](../../../docs/advanced-usage.md#установка-на-windows).

После установки обнови текущее окружение процесса доступным безопасным способом или попроси пользователя перезапустить терминал/IDE. Затем повтори только проверки версий.

Установи `review-tasks` через `pipx` из текущей папки:

- ZIP-архив релиза — обычная установка;
- Git checkout — editable-установка.

Не считай установку успешной, пока исполняемый файл `review-tasks` не доступен по PATH и `review-tasks --help` не работает в окружении будущего запуска. Если работает только `python -m review_tasks`, исправь PATH, точку входа или выбранное окружение Python по [диагностике](../../../docs/troubleshooting.md#review-tasks-не-находится-в-path). Это проблема установки, а не готовый способ запуска. Не переустанавливай работающий пакет, если достаточно исправить PATH.

Опционально предложи KDiff3 для сравнения кода задачи/MR; его отсутствие не мешает завершить настройку AI-ревью. При выборе проверь наличие приложения в PATH или стандартном каталоге, устанавливай только по просьбе пользователя. Нестандартный путь к `.exe` или выбор Meld/WinMerge задаётся через `[diff_viewer]` по [инструкции](../../../docs/advanced-usage.md#полные-изменения-во-внешнем-diff-инструменте). После `review-init` сравнение открывается кнопкой «Открыть изменения» в расширении Jira или через `_review_info/changes/open-changes.cmd` в каталоге задачи.

## 4. Подготовить репозиторий проекта и Git-доступ

После готовности Git и CLI запроси локальный путь или Git URL репозитория проекта.

Если пользователь дал URL:

1. запроси каталог клонирования, если он не указан;
2. для SSH URL проверь сетевую доступность SSH-сервиса GitLab безопасной проверкой без аутентификации; не читай приватные ключи и не изменяй SSH-конфигурацию;
3. если хост доступен, но SSH-аутентификация не настроена, используй [«Общий SSH-доступ к GitLab»](../../../docs/advanced-usage.md#общий-ssh-доступ-к-gitlab): пользователь запускает `ssh-keygen` без параметров и добавляет открытый ключ в GitLab; не пытайся исправлять сетевую недоступность созданием нового ключа; при ошибке из-за кириллического пути настрой ASCII-каталог и явную конфигурацию SSH по тому же разделу;
4. для HTTPS URL закрытого репозитория не проси токен и не помещай его в URL или командную строку; пользователь проходит авторизацию через Git Credential Manager;
5. после готовности доступа клонируй репозиторий в согласованный каталог.

Для локального или только что клонированного репозитория:

1. проверь корень Git-репозитория;
2. проверь URL выбранного remote; не выводи встроенные в URL учётные данные, если они там присутствуют;
3. проверь неинтерактивный доступ к remote с отключёнными запросами учётных данных и ограничением времени ожидания по [рецепту](../../../docs/advanced-usage.md#remote-и-ветка-задачи); не запускай проверку, которая может зависнуть в ожидании пароля, токена или подтверждения;
4. выполни `git fetch <remote> --prune`;
5. проверь, что выбранный ref существует после fetch;
6. проверь, что `reviewsRoot` находится вне репозитория проекта и доступен для записи; если каталога нет, создай его после сообщения пользователю.

Не исправляй remote, SSH-конфигурацию или учётные данные автоматически. При ошибке различай сетевую недоступность, ошибку аутентификации и ошибку Git; покажи пользователю только безопасную причину, помоги исправить доступ и повтори отказавшую проверку.

## 5. Подготовить AI-агента

Для ручного запуска достаточно готовой авторизованной IDE-сессии. Для запуска из Jira нужен headless CLI выбранного агента.

Если ни Codex, ни Cursor, ни OpenCode не готовы, предложи пользователю выбрать один. После выбора и команды «установи» используй типовую Windows-установку из [«AI-агент»](../../../docs/advanced-usage.md#ai-агент). Не устанавливай несколько агентов без просьбы.

Для OpenCode не полагайся на `latest` другого npm-пакета и не переходи между major-версиями. Установка и обновление поддерживаемой линии выполняются только так:

```powershell
npm install -g opencode-ai@1
opencode --version
```

Результат `opencode --version` MUST начинаться с `1.`. Если обнаружены `@opencode/cli` или major V2, не считай компонент готовым. В рамках уже разрешённой пользователем установки удали `@opencode/cli`, установи `opencode-ai@1` и повтори проверку. Не сохраняй V2 рядом с V1: оба пакета регистрируют команду `opencode`.

Для ручного запуска проверь готовую авторизованную IDE-сессию; отдельный headless CLI не обязателен. Для Jira выполни существующие команды из [«Проверить headless CLI»](../../../docs/advanced-usage.md#проверить-headless-cli) только для выбранного агента. Для OpenCode используй контракт V1: `opencode --version`, `opencode run --help`, `opencode auth list` и `opencode models routerai`; не применяй инструкции или проверки V2. Авторизацию выполняет пользователь по стандартной процедуре входа. Не проси учётные данные в чате и не отправляй тестовый запрос.

## 6. Настроить OpenCode и RouterAI

Выполняй раздел только при выборе OpenCode V1 и необходимости RouterAI. При готовой авторизации и рабочем провайдере сохрани существующие настройки. Провайдер и доступные модели настраиваются в OpenCode; отдельная модель ревью Jira сохраняется в проекте на шаге 9 и не меняет глобальную модель. Используй только формат V1 из локального примера; не преобразуй `provider` в `providers`, `npm` в `package` или `options` в `settings`.

Каталог глобальной конфигурации: `%USERPROFILE%\.config\opencode`. Выбери ровно один целевой файл:

1. существующий `opencode.jsonc`;
2. иначе существующий `opencode.json`;
3. иначе новый `opencode.jsonc`.

Если существуют оба файла, до изменения перечисли только конфликтующие пути ключей без значений, предложи `opencode.jsonc` как основной и создай резервные копии с отметкой времени обоих файлов. Консолидацию выполняй только после согласия пользователя.

Добавь провайдера RouterAI и модель по умолчанию объединением настроек по [примеру](references/opencode-routerai.example.jsonc). Не перезаписывай несвязанные ключи. Ключ API записывай только как `{env:ROUTERAI_API_KEY}`.

Проверка без платного запроса: `opencode --version`, затем `opencode models routerai`.

## 7. Настроить секреты и MCP

Проверяй только зависимости выбранного режима:

- MCP `off` — переменные окружения MCP и конечные точки не нужны;
- MCP `required` — проверь наличие `RDV_MCP_1C_URL` и `RDV_MCP_1C_TOKEN`; формат хоста и пути заданы в документации и реестре из поставки;
- RouterAI — нужен `ROUTERAI_API_KEY`;
- запуск из Jira — нужен локальный токен расширения; учётные данные GitLab API нужны только при выборе поиска MR, для TASK-режима они не требуются.

Если секрет внешнего сервиса отсутствует, останови только зависимый этап. Сообщи точное имя переменной окружения и попроси пользователя самостоятельно создать токен и задать переменную окружения в пользовательских или системных переменных окружения Windows или защищённой сессии. После подтверждения проверь только наличие в окружении будущего запуска. После изменения пользовательских или системных переменных окружения перезапусти IDE/терминал, из которого запускается сервис, и сам сервис: дочерний процесс старой IDE может снова получить старые значения. Значения из отдельной пользовательской сессии не появляются автоматически в процессе агента или сервиса.

Доступность конечных точек MCP и ожидаемых инструментов до создания каталога задачи не проверяй и не делай условием завершения настройки. В отчёте укажи, что проверено наличие переменных окружения; соединение проверяется при работе с подготовленной задачей.

Секреты внешних провайдеров, `RDV_MCP_1C_TOKEN` и токены GitLab API не записывай в `prefix-config.json`, `service.json`, Markdown или общедоступные примеры.

## 8. Настроить запуск из Jira

Выполняй раздел только если пользователь выбрал запуск из Jira. Для ручного запуска из IDE пропусти его.

Для автоматической настройки используй `review-tasks local-service config` по [инструкции](../../../docs/advanced-usage.md#запускать-ревью-из-jira), задавая параметры только выбранного агента. `config-jira-local-review-service.bat` оставь как вариант самостоятельной интерактивной настройки пользователем. Сохрани существующий локальный токен расширения; если его нет, сгенерируй новый, запиши в конфигурацию сервиса и передай пользователю для всплывающего окна. Этот локальный токен допускается в выводе; внешние ключи API по-прежнему запрещены.

Запусти сервис и проверь `/health` через loopback-адрес на хосте и порту из действующей конфигурации. Только после успешной проверки работоспособности попроси пользователя:

1. открыть `chrome://extensions`;
2. включить Developer mode;
3. загрузить распакованное расширение `extension/jira-local-review-extension` из текущей рабочей копии;
4. задать URL/порт сервиса и локальный токен расширения во всплывающем окне;
5. проверить, что расширение может прочитать конфигурацию проекта через сервис.

MCP задаётся в конфигурации проекта переключателем `useMcp` и хранится как `mcp_enabled`: `true` → `required`, `false` → `off`. Отсутствующее поле означает `true`. Сервис явно передаёт выбранный режим в `init`; в `off` переменные окружения MCP и файлы подключения MCP не требуются. Это настройка проекта, а не переопределение для отдельного Jira-запуска. Проверки остальных файлов задачи и выбранного агента сохраняются.

## 9. Сохранить проект и выполнить финальную проверку

После успешных проверок сохрани поддерживаемые движком параметры проекта по разделу [«Сохранить параметры проекта»](../../../docs/advanced-usage.md#сохранить-параметры-проекта).

Сохрани выбранные `ide` и `mcp_enabled` вместе с параметрами проекта по тому же разделу. Для Jira с OpenCode при отдельном выборе модели ревью сохрани полный `provider/model` через `opencodeModel` API проекта (`opencode_model` в файле); пустое значение оставляет штатный выбор OpenCode. При непустом значении проверь наличие `--model` в `opencode run --help`. Ручной `review-init` использует IDE и MCP как значения по умолчанию и передаёт явные флаги CLI; параметры пользователя имеют приоритет. Не рассчитывай на сохранность текущего диалога.

Проверь финальное состояние по [setup-checklist.md](references/setup-checklist.md). Не запускай тестовый `review-tasks init`: он создаёт каталог задачи и требует реальную задачу/MR.

Следующий этап — `review-init`. Он получает задачу/MR, принимает параметры конкретного запуска и использует конфигурацию префикса для недостающих значений. Вопросы о ключе задачи, ref и других параметрах ревью допустимы; установка и исправление Git-доступа остаются в `review-setup`.

## Итоговый отчёт

Сообщи:

- что установлено и проверено;
- репозиторий проекта, remote и ref;
- путь `reviewsRoot`;
- выбранные IDE и режим MCP;
- путь сохранённой конфигурации префикса без секретов;
- для секретов внешних сервисов только `present` / `missing`; локальный токен расширения можно передать пользователю;
- готовность ручного и, если выбран, Jira-запуска;
- оставшиеся ручные этапы проверки.

Не называй настройку завершённой, если обязательный пункт выбранного режима не проверен.
