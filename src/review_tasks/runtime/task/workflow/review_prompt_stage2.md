# Ревью BSL-кода {{TASK}} — СТАДИЯ 2

Начинай только после успешной валидации Stage 1.

Stage 2 подтверждает или отклоняет каждого кандидата Stage 1. Получи полный упорядоченный список командой `review-tasks stage1-list-candidates`. Для каждого кандидата сначала полностью подготовь предметное решение, затем запиши его командами `review-tasks stage2-*`. После обработки всех кандидатов запиши публичный результат, провалидируй Stage 2 и запусти рендерер.

Stage 2 завершен только когда: каждый кандидат имеет один успешно записанный `finding`; публичные поля записаны; `validate-review-yaml` завершился с кодом 0; `renderer` завершился успешно. До выполнения всех четырёх условий работа не завершена.

## Инварианты Stage 2

Ты **ОБЯЗАН** соблюдать эти инварианты при выполнении этапа Stage 2. Нарушение любого инварианта делает дальнейшее выполнение Stage 2 недопустимым.

- Получи полный упорядоченный список кандидатов только командой `review-tasks stage1-list-candidates`.
- Получи отзывы эксперта-ревьюера командой `review-tasks read-feedback --task {{TASK}}`. Команда `read-feedback` возвращает `feedback` эксперта-ревьюера о предыдущих замечаниях этой задачи. Применимые указания эксперта-ревьюера в `comment` **обязательны**: если текущий кандидат подпадает под явное исключение, запиши для него `drop` с объяснением в `drop_reason`. Пустой успешный вывод или ошибка чтения означают, что `feedback` отсутствует, не учитывай их.
- Ты **ДОЛЖЕН** для каждого candidate выполнить предметный анализ **только один раз**; не составляй промежуточный сводный список решений по всем candidate перед записью. 
- Не возвращайся к повторному полному анализу уже выполненного `candidate` и не пересматривай `decision`; Ты должен следовать процессу **Анализируй candidate → фиксируй итоговые поля → переходи к следующему**.
- Обработай **каждый** исходный `candidate-N`, возвращённый командой `review-tasks stage1-list-candidates`, по порядку и по одной политике принятия решения; для каждого создай ровно один `finding`. Глубина анализа зависит от сложности и остаточной неопределённости, но при любой глубине анализа требуется собрать доказательства, выполнить `self_check`, применимые `standard_hints`, `verification`, `decision` или запись `finding`.
- Для `keep` обязательно передавай `suggestion-text` со значением, сформулированным по правилу `suggestion`.
- Для `keep` опционально передавай `suggestion-code-file` **только если короткий пример кода яснее текста показывает нужное условие или последовательность действий при исправлении**. Показывай один фрагмент в месте исправления: обычно 3–10 строк, не более 15. Не переписывай функции/процедуры целиком и не включай большой объём неизменённого кода.
- Не читай, не изменяй и не выводи stage YAML напрямую: `_review_info/review_result_stage1.yaml` и `_review_info/review_result_stage2.yaml`. Список кандидатов получай только через `review-tasks stage1-list-candidates`, результат Stage 2 изменяй только командами `review-tasks stage2-*`.
- Не открывай и не читай `_review_info/review_lines.json`. Не изменяй Stage 1 и не вызывай изменяющие команды `review-tasks stage1-*`.
- Не придумывай и не изменяй идентификаторы, не создавай новые идентификаторы `candidate` и `findings` для дефектов, которым не соответствует кандидат из этого списка.
- Не запрашивай один `standard ID` через MCP повторно в пределах Stage 2. Если результат уже есть в контексте — используй его.

## Как читать `review_bsl.md`

Анализируй только BSL-блоки из `review_bsl.md`. Основной фокус — новые TARGET-строки в `-- new bsl --`, особенно строки с `+`; непомеченный контекст используй для проверки влияния изменения. `-- old bsl --` нужен только для понимания замены и не содержит TARGET-координат.

`start_line` и `end_line` бери из TARGET-строк `review_bsl.md`, соответствующих `file` кандидата. Уточняй координаты минимальным достаточным непрерывным диапазоном видимых TARGET-строк, который доказывает `observation`. Диапазон должен содержать все видимые строки, используемые как доказательство: не ссылайся в `observation` на строку вне диапазона как на часть доказательства; если необходимые строки разделены, расширь диапазон так, чтобы он содержал их все.

Комментарии `//...` не являются исполняемым кодом; в многострочной строке частью значения являются строки с `|...`, например `Запрос.ТекстЗапроса`. 

Не считай дефектом незавершённую конструкцию на границе BSL-блока: её продолжение может быть вне видимого фрагмента.

## Анализ `finding` до записи

До записи `finding` выполни для кандидата все шаги:

1. Проверь подозрение по всему относящемуся видимому контексту. Минимальный доказывающий TARGET-диапазон укажи в `start_line` и `end_line`.
2. Сформулируй `observation` для разработчика, который ещё не видел код и ход проверки. Сначала назови ситуацию и ошибочный результат для операции или данных. Затем объясни, какое действие кода к нему приводит и при каком условии. Условие укажи рядом с зависящим от него выводом. Если дефект можно доказать только через ожидаемое техническое или бизнес-поведение, назови это поведение. Не начинай с перечня артефактов и шагов проверки.
3. **Выполни предварительный `self_check`.** Сформулируй наиболее сильную правдоподобную безопасную альтернативную интерпретацию и проверь её по видимому материалу. Результат сохрани в `alternative_interpretation`.
4. Сформулируй точные вопросы `verification`, затем проверь все привязанные `standard_hints` и при необходимости используй дополнительные способы проверки. Основной источник вывода укажи в `source`. Подготовь по одному `channel` для каждого реально использованного канала проверки и по одной `trace` для каждого необходимого межстрочного обязательства.
5. Установи, подпадает ли кандидат под указания `comment` эксперта-ревьюера из `feedback`. Область действия `feedback` определяй по комментарию, строкам кода и контексту прежнего замечания.
6. С учётом доказательств, `self_check`, `verification`, `traces` и применимых `feedback` оцени `confidence` и `false_positive_risk`, затем примени раздел «Политика решения `keep`/`drop`». `confidence` показывает уверенность в правильности выбранного решения; `false_positive_risk` — риск того, что исходное подозрение не является реальным дефектом.
7. Для `drop` сформулируй конкретную причину — `drop_reason`. Если `drop` вызван применимым `feedback` эксперта-ревьюера, `drop_reason` называет этот `feedback` и его связь с текущим кандидатом. Для `keep` оцени влияние дефекта — `severity` и сформулируй финальную рекомендацию по исправлению — `suggestion`: назови изменение кода или данных, которое устраняет причину, описанную в `observation`. Если выбрать изменение нельзя без недостающего сведения, укажи, что именно нужно выяснить и какая правка потребуется при подтверждении.

`self_check` и `verification` независимы: первый проверяет собственный вывод, вторая хранит внешние и нормативные основания. Одно не заменяет другое.

Заверши анализ, когда выполнены обязательные проверки, завершён `self_check` и собранных доказательств достаточно для применения раздела «Политика решения `keep`/`drop`».

## Политика решения `keep`/`drop`

Stage 1 намеренно собирает подозрения широко. Выбери для каждого кандидата `keep` или `drop` после проверки конкретного паттерна по всему относящемуся видимому контексту.

### Выбор `keep`

Выбирай `keep`, если видимый код или `verification` подтверждают конкретный механизм дефекта либо нарушение явного бизнес- или технического правила. Применимый `feedback` эксперта-ревьюера имеет приоритет: кандидат, подпадающий под явное исключение из `feedback`, не публикуется как `keep`.

Существенный риск, который трудно окончательно подтвердить разрешённым материалом, можно сохранить как `keep`, если видимый код поддерживает конкретный правдоподобный причинный механизм, а потенциальное последствие существенно влияет на корректность, целостность данных, безопасность, транзакции или поведение интеграции.

В таком случае:

* в `observation` отдели наблюдаемые факты от вывода о риске;
* честно оцени `confidence` и `false_positive_risk`;
* сформулируй и проверь наиболее сильную правдоподобную безопасную альтернативную интерпретацию;
* подготовь конкретный `missing_context`;
* при необходимости добавь вопрос в `questions_to_author`.

Не публикуй низкоуверенное замечание при несущественном риске.

### Выбор `drop`

Если конкретного правдоподобного механизма нет либо риск основан только на предполагаемом намерении, невидимом бизнес-правиле, окружении, конфигурации или метаданных, выбирай `drop` и не додумывай контекст.

В частности:

* предполагаемое намерение или невидимое бизнес-правило — `drop`; добавь вопрос в `questions_to_author`, только если ответ автора может изменить вывод;
* предположение о невидимом окружении, конфигурации или метаданных — `drop`; добавь конкретный отсутствующий материал в `missing_context`;
* оформление, имя, опечатка, магическая константа или стилистика без влияния на поведение — `drop`.

`drop` допустим после проверки конкретного паттерна в конкретных строках либо при соответствии явному исключению эксперта-ревьюера по `feedback`. Не используй причины «покрыто другой находкой», «маловероятно», «несущественно» или «сводится к стилю» вместо контр-проверки.

Вопросы и недостающий контекст дополняют результат, но не заменяют решение `keep` или `drop`.

**Запрет консолидации.** Одна точка паттерна — один `finding`; разные исходные кандидаты не схлопывай, даже если они относятся к одному классу дефекта.

### Нормативная `verification`

`standard_hints` — маршруты проверки текущего кандидата из вывода `review-tasks stage1-list-candidates`: `dev_standard_ids`, `bsp_files` и `platform_index_files`. Для каждой привязанной подсказки выполни отдельную проверку.

Для кандидата, исключённого на основании `feedback` от эксперта-ревьюера внешние проверки не требуются, каналы `verification` не готовь.

Для каждого элемента `standard_hints`:

1. Сформулируй конкретное проверяемое утверждение, которое можно подтвердить или опровергнуть. Не используй формулировки вида «проверить применимые стандарты».
2. Прочитай привязанный локальный источник.
3. Явно активируй `mcp-review-verification`, выбери указанную ниже reference и проверь то же утверждение.
4. Сопоставь оба результата с видимым кодом и рассматривай их как доказательства, а не готовое решение. Учитывай их при выборе `decision` по разделу «Политика решения `keep`/`drop`».

Маршрутизация:

- `dev_standard_ids` с `stdN` → прочитай локальную краткую карточку, выбери `references/v8std-standards-diagnostics.md` и получи полный официальный standard через v8std MCP;
- `dev_standard_ids` с `rdvN` → используй локальную корпоративную карточку как declared RDV source; не запрашивай несуществующую v8std page и не утверждай, что полный корпоративный standard получен через v8std MCP;
- `bsp_files` → для каждого имени модуля выбери `references/ssl-library-search.md` и выполни описанный в ней полный контракт проверки;
- `platform_index_files` → выбери `references/platform-docs.md`.

Не повторяй тот же MCP-запрос без нового вопроса или новых входных данных. Дополнительный канал используй только для конкретного вопроса, ответ на который способен изменить `decision`, `confidence` или `false_positive_risk`. Для каждого `finding` отдельно реши, нужна ли дополнительная внешняя проверка: высокая `confidence` или `source: ai_knowledge` сами по себе не доказывают её ненужность. Если она не нужна и нет `standard_hints`, каналы `verification` не готовь.

### Межстрочные `traces`

`trace` нужна, когда доказательство зависит от связи строк: одна строка создаёт обязательство, последующий код его выполняет или нарушает. Зафиксируй строку возникновения, требуемое действие, исход и видимую строку выполнения или нарушения, если она есть.

Определи исход:

- `satisfied` — обязательство видимо выполнено; зафиксируй строку закрытия;
- `violated` — видимые строки доказывают нарушение обязательства: выполнено несовместимое действие, использован ошибочный результат или достигнута точка, после которой позднее выполнение уже не устраняет дефект; зафиксируй строку нарушения, если она есть;
- `not_visible` — видимого материала недостаточно, чтобы доказать выполнение или нарушение; обязательство ещё могло быть выполнено за пределами фрагмента. Добавь конкретный отсутствующий материал в `missing_context`.

Выбранный статус определяет смысл `trace`; указанная строка его не изменяет. Не создавай `finding` только из-за `not_visible`: это не самостоятельное основание для `keep`. Без межстрочного обязательства `trace` не создавай.

`violated` может быть основанием для `keep`, если связь строк доказывает механизм дефекта. Межстрочная природа доказательства сама по себе не повышает `false_positive_risk`.

## Последовательный блок записи

Не начинай запись кандидата, пока не готовы все базовые поля, `self_check`, необходимые `verification.channels`, `traces`, `decision` и финальный `drop_reason` либо `severity` и `suggestion`.

Для каждого кандидата выполняй команды последовательно: `finding` → `channels` → `traces`. Пустые шаги `channels` или `traces` пропускай. После первого результата, не соответствующего описанному ниже контракту успеха, останови блок. К следующему кандидату переходи только после успешного завершения всего блока.

1. Один `review-tasks stage2-upsert-finding` со всей базовой частью `finding`:

```powershell
review-tasks stage2-upsert-finding --candidate <candidate-N> --start-line <N> --end-line <N> --observation <text> --source <ai_knowledge|trigger_match|std|rdv|ssl|platform_docs|v8std|mixed> --confidence <high|medium|low> --false-positive-risk <low|medium|high> --decision <keep|drop> [--alternative-interpretation <text>] [--drop-reason <text>] [--severity <critical|important|desirable>] [--suggestion-text <text>] [--reset-details]
```

Не передавай `--area` и `--file`: их копирует CLI. Если по инварианту требуется код, создай `_review_info/tmp`, запиши только сырой BSL без Markdown в `_review_info/tmp/<candidate-N>-suggestion.bsl` в UTF-8 без BOM и передай файл через `--suggestion-code-file`. `_review_info/tmp` не является результатом ревью. Для `candidate-N` используй только связанный с этим кандидатом файл `_review_info/tmp/candidate-N-suggestion.bsl`. Файл другого кандидата запрещён.

1. Если `verification-channel` нет, пропусти шаг. Иначе вызови команду для каждого подготовленного `verification-channel`:

```powershell
review-tasks stage2-upsert-verification-channel --candidate <candidate-N> --capability <identity> --hypothesis <text> --status <applied|unavailable> --result-note <text>
```

1. Если `traces` нет, пропусти шаг. Иначе вызови команду для каждой подготовленной `trace`:

```powershell
review-tasks stage2-upsert-trace --candidate <candidate-N> --established-at <N> --obligation <text> --status <satisfied|violated|not_visible> [--satisfied-at <N>]
```

### Проверка результата и восстановление

После каждого вызова `review-tasks stage2-upsert-finding`, `review-tasks stage2-upsert-verification-channel`, `review-tasks stage2-upsert-trace` и `review-tasks stage2-set-result` проверь результат. Успех одновременно требует: код завершения `0`, `ok:true`, логический тип поля `changed` и, для каждой команды `review-tasks stage2-upsert-*`, поле `candidate`, равное текущему кандидату. `changed:false` — успешная операция без изменения данных. YAML и содержимое `finding` в `stdout` быть не должны.

Любое несоответствие этому контракту, включая `ok:false`, неправильный `candidate` или значение `changed` не логического типа при коде завершения `0`, останавливает текущий блок.

Не читай, не изменяй, не удаляй и не перекодируй управляемый CLI файл Stage 2. В частности, не диагностируй его через `Get-Content` или `chcp`: команда записи хранит UTF-8 и при ошибке оставляет файл без изменений.

Если команда завершилась с ненулевым кодом и `stderr` содержит конкретную исправимую причину, исправь аргументы команды или входной файл `suggestion` и повтори только упавшую команду. Не повторяй уже успешно завершённые команды. Код завершения `0` с нарушенным контрактом успеха считай ошибкой CLI: не пытайся исправлять её изменением данных `finding`. Если причина не исправляется допустимыми входами команды, останови процесс и сообщи об ошибке CLI.

## Завершение

После всех кандидатов один раз в первичном штатном процессе вызови `review-tasks stage2-set-result`. Передай итог в 1–3 предложениях через `--summary`, а все подготовленные вопросы и недостающий контекст — повторяемыми `--question` и `--missing-context` в порядке отчёта. Отсутствие повторяемых аргументов означает пустой список. Не дублируй `findings` с `keep` в публичных полях.

```powershell
review-tasks stage2-set-result --summary <text> [--question <text>]... [--missing-context <text>]...
```

Затем выполни:

```powershell
review-tasks validate-review-yaml --input _review_info/review_result_stage2.yaml
```

При ошибке валидации исправь только соответствующую секцию и повтори валидацию:

- базовые поля или `suggestion` → `review-tasks stage2-upsert-finding` без `--reset-details`;
- `channel` → `review-tasks stage2-upsert-verification-channel`;
- `trace` → `review-tasks stage2-upsert-trace`;
- публичные поля → `review-tasks stage2-set-result` с повторной передачей `--summary` и всех `--question` и `--missing-context`.

Обычный `review-tasks stage2-upsert-finding` сохраняет существующие `channels`, производные поля `verification` и `traces`.

`--reset-details` используй только для удаления `channel` с ошибочным `capability`, `trace` с ошибочным `established_at`/`obligation` или намеренной полной пересборки деталей `finding`. Вызови `review-tasks stage2-upsert-finding --reset-details` со всеми корректными базовыми полями без искусственного изменения, затем заново запиши необходимые `channels` и `traces`. Повторяй валидацию до кода `0`.

После кода `0` выполни:

```powershell
review-tasks render-review-report --input _review_info --output review-report-{{KEBAB_TASK}}.md
```

Рендерер создаёт Markdown-отчёт и `_review_info/review_result.yaml`. Не создавай `_review_info/review_result.yaml` вручную.
